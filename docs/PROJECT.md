# 家政预约与调度平台项目说明

## 1. 项目目标与边界

项目中文名称为“家政预约与调度平台”，GitHub仓库名为 `home-service`。这是一个面向 Java 后端实习求职的家政预约与履约调度项目，采用平台管理型模式，不做服务人员自由定价的 C2C 市场。

项目的核心不是把菜品换成家政服务，而是解决：

- 服务规格、技能、排班和时间资源匹配；
- 标准预约自动派单与优惠预约自主抢单；
- 模拟支付、报价变化、超时退款和状态流转；
- 同一订单竞争与同一人员时间槽竞争；
- 三端业务闭环、实时通知和可审计的历史记录。

原来的“普通订单依次邀请人员、紧急订单抢单、管理员兜底派单”方案已经废弃，后续不得同时保留两套流程。

## 2. 参考工程的继承方式

新会话不需要重新读取 hmall、苍穹外卖和黑马点评源码，按以下结论执行：

- **hmall 为主要工程规范**：采用模块化单体、MyBatis-Plus、`domain/{dto,po,query,vo}`、Service/Impl、Mapper、统一分页、异常体系、枚举、配置和拦截器等清晰分层。
- **苍穹外卖提供多端业务组织思路**：客户、服务人员和管理员接口分组；请求 DTO、响应 VO、统一结果、认证上下文、配置属性和全局异常相互分离。只吸收结构，不复制外卖业务，也不采用字段注入。
- **黑马点评提供并发思维**：先识别真正竞争的资源，再使用条件更新、幂等、缓存或 Lua。Redis 只在有明确价值时加入，数据库始终承担最终一致性。

当前项目使用一个后端应用和一个前端工程。后端按已确认要求采用 Maven 父工程继承与聚合、子模块按需声明依赖，参考 hmall 和苍穹外卖的工程组织；多 Maven 模块仍构成一个 Spring Boot 应用和部署单元，不拆成微服务。

课程源码与 JDK 17、Spring Boot 3.5、本文档或 `AGENTS.md` 冲突时，以当前项目规范和现代写法为准，不机械复制旧代码。

## 3. 角色、账号与权限

### 3.1 三类角色

- 客户：注册登录、浏览服务、维护地址、创建和支付预约、调整优惠报价、取消、查看进度和评价。
- 服务人员：登录、设置排班和请假、查看并抢优惠订单、查看标准派单、执行履约状态操作。
- 管理员：维护账号、服务、价格、技能和基础配置，查看订单、调度、支付与异常；不手工指定派单人员。

### 3.2 账号规则

- 使用统一认证账号 `auth_account` 保存登录凭证、角色、启停状态和公共联系资料。客户没有额外独立属性，`customerId` 直接使用角色为 `CUSTOMER` 的账号ID，不单建客户资料表；服务人员通过 `worker_profile.account_id` 关联账号，`workerId` 使用人员表主键，不能与账号ID混用。JWT主体和 `UserContext` 使用 `accountId`。
- 客户可以自行注册；服务人员账号由管理员创建；当前只有初始化超级管理员，不做复杂 RBAC。
- 三端使用用户名和密码登录，手机号只作为联系方式；密码使用 BCrypt 等专用哈希算法，禁止明文和 MD5。
- 三端具有独立登录入口并校验角色权限，认证逻辑可以复用。
- 账号只保留启用、禁用；服务人员另有“允许派单”业务状态。
- 认证采用 hmall 的整体思路：参考 `JwtTool`、登录拦截器和 ThreadLocal `UserContext`，但按本项目规范重新实现。
- 只签发 JWT访问令牌，不实现刷新令牌、Redis登录会话或 Token黑名单；Token使用 HS256，载荷至少包含 `accountId` 和 `role`。
- HTTP请求统一使用 `Authorization: Bearer <JWT>`；拦截器解析前去除 `Bearer ` 前缀，校验签名、有效期、角色和账号可用状态，并在请求结束后清理用户上下文。
- Token有效期和接口白名单配置化；HS256密钥必须具有足够强度，通过环境变量或本机配置提供，不得硬编码或提交Git。
- 因为没有刷新令牌和黑名单，退出登录只删除客户端令牌，已签发令牌在到期前不能主动撤销。
- 暂不实现微信登录、短信验证码、忘记密码、主动注销账号和强制下线。

## 4. 服务目录与价格

服务目录采用：

> 服务分类 → 服务项目 → 服务规格 SKU

服务分类、项目、SKU、技能、服务区域及客户端入口均由接口和数据库维护，前端不维护固定业务注册表。`listClientEntries` 返回稳定 code、服务类型、分组、名称、说明、排序、可预约状态和绑定 SKU 完整展示信息；前端据此分组和渲染。入口 code 为有格式约束的普通字符串，其具体值由数据库初始化数据产生，不从分类名称或顺序猜测。未绑定、下架等不可预约原因由接口返回，客户端不寻找替代 SKU。管理员通过接口选择入口；创建和更新 SKU 必须明确发送 `clientEntryCode` 字符串或 null，后者表示不绑定或解除绑定。

每个 SKU 至少表达名称、标准价格、预计时长、计价单位、所需技能、上下架状态、服务说明以及是否支持优惠预约。预计时长必须是 30 分钟的整数倍。

入口绑定使用可空的 `service_sku.client_entry_code`，未绑定时保存 `NULL`，不保存空字符串。唯一约束 `uk_service_sku_client_entry(client_entry_code)` 允许多个 SKU 不绑定入口，但同一非空入口编码最多绑定一个 SKU；下架仍保留绑定。SKU 逻辑删除时，必须在同一事务内将 `client_entry_code` 清为 `NULL`，释放入口，不保留已删除 SKU 的旧绑定，也不另建绑定历史表。历史订单继续使用订单快照。Service 仍须校验入口存在及服务类型匹配，并将入口绑定唯一冲突转换为契约已有的 `CONFIG_CONFLICT`，不能只依靠数据库唯一约束完成业务校验。

### 4.1 首批服务

- 清洁 / 日常清洁：面向已入住住宅的常规打扫，提供 2 小时、3 小时、4 小时固定套餐。
- 清洁 / 深度清洁：面向已入住住宅的重点区域精细清洁，按固定面积区间形成规格，但每张订单数量仍为 1。
- 维修 / 管道与卫浴：可包含疏通马桶、维修马桶、维修水龙头、更换同规格水龙头等项目。
- 维修 / 电气与灯具：可包含更换灯泡、更换普通灯具、更换同规格保险丝等项目。
- 维修 / 家电维护：可包含空调清洗等服务边界明确、能够预先确定价格和预计时长的项目。

维修项目通过后台配置具体项目和 SKU，不把“水龙头更换”写成唯一维修业务。每个维修 SKU 必须明确包含内容、排除内容、是否由客户自备配件、标准价格、预计时长和所需技能；当前维修仍只支持标准预约，不支持人员现场议价或接单后加价。

深度清洁不等同于装修后的开荒保洁。开荒保洁、多数量服务和无法预先确定服务边界、必须上门检测后报价的维修暂不进入当前范围。

### 4.2 两种预约方式

- 标准预约：按标准价格模拟支付，由系统直接自动派单，人员不接受或拒绝。
- 优惠预约：当前日常清洁和深度清洁的已上架 SKU 均支持；客户还需满足第 6.2 节的预约提前量，并在平台范围内报价，由符合条件的人员自主抢单。

服务人员不能自行定价或还价。订单金额表示客户订单成交价，人员端不将其展示为人员收入。工资、抽成、绩效结算和提现不在当前范围，也不提前建表。

### 4.3 优惠报价

- 每个支持优惠的 SKU 配置最低报价，初始化数据可取标准价约 80%。
- 优惠报价统一为 `priceStep` 的整数倍、不低于订单最低报价快照且严格低于订单标准价快照。当前步长为 `"5.00"`，前端必须读取 `getBookingRules`，不得另设常量。最低价向上对齐后若无合法报价则不可优惠预约。不保留浏览器旧订单专用规则或 `offerPriceRule` 字段；标准单不携带无意义的优惠规则。
- 报价达到标准价时不再属于优惠报价；“补差转标准预约”放在基础闭环完成后的增强阶段。
- 未被接单且未截止时，客户可以加价或降价；人员接单后成交价格锁定。
- 加价需要完成模拟补差；降价需要在同一事务内记录部分模拟退款。
- 报价变化保留历史记录并递增 `priceVersion`，不得覆盖后丢失历史。
- WebSocket主动推送报价变化，但抢单必须携带预期价格和版本。旧版本请求返回报价已变化，不静默按新价格成交。

金额统一使用 `BigDecimal` 与数据库 `decimal`，禁止使用 `double`。

## 5. 地址与服务区域

- 客户可以维护多个地址，仅填写联系人、联系电话、省市区编码及名称、详细地址和默认标记。坐标由系统维护，当前未接地图服务，允许为空且不阻止按城市预约；地址写入DTO不接收坐标。仅改联系人、电话或默认标记保留系统坐标，实际地址变化时旧坐标失效为空。订单地址使用独立不可变输出快照，不受地址簿和未来坐标更新影响。
- 客户可自助编辑称呼和个人联系电话，用户名仅展示。个人资料、地址联系人和订单本次联系人各自独立，修改时不互相无提示覆盖。
- 预约默认带入默认地址及其联系人，客户可覆盖本次联系人和电话，仅保存订单快照。默认状态只保存在地址的 `is_default`，账号不另存默认地址ID。首个地址自动默认；存在有效地址时恰有一个默认地址，没有有效地址时没有默认地址。删除或取消默认标记后，选择最早创建的其他有效地址；创建时间相同时按地址ID确定顺序。仅有一个有效地址时，取消默认标记仍保留它为默认地址。
- 所有可能影响默认地址的新增、修改、删除操作，必须在事务内先按主键锁定同一客户的 `auth_account` 账号行，再以当前读读取并修改其地址；统一遵守“客户账号行 → 该客户地址行”的锁定顺序，并在持锁期间维护上述默认规则。不能仅凭 `@Transactional` 或“先查询再修改”宣称解决并发；不使用 Redis 或 JVM 锁替代该数据库事务方案。
- 订单创建时保存联系人、地址和服务内容等必要快照，后续资料修改不影响历史订单。
- 预约可选提供至多3张现场图片，每张不超过5 MiB，仅 JPEG/PNG/WebP，上传需验证内容并清理 EXIF。订单保存不可变图片关联；未关联订单的本人临时图片可删除，历史附件不可随地址或目录编辑变化。图片经角色和订单资格鉴权后读取，不提供公开列表或公开 URL。
- 下单时校验图片数量不超过3张、图片ID不重复、归属当前客户且可用，按请求数组顺序写入 `order_scene_image.sort_no`，与订单创建在同一事务内保存。保留 `(order_id, image_id)` 唯一约束，排序字段不设唯一索引，不增加替代此索引的表或复杂机制。
- 符合接单资格的人员在抢单前可查看客户主动提供的现场图片，仍不得获取结构化完整门牌、电话和开始码。提示客户避开个人隐私；图片不保证接单、不扩大范围、不允许现场议价。
- 当前服务区域为广东省广州市全部区，只按城市筛选人员，不计算距离、不记录轨迹、不按距离收费。
- 当前固定缓冲是简化模型，不声称反映广州真实道路通勤时间。
- 未来可用地图 API 做地理编码和路线时间；Redis GEO只能做坐标附近查询和近似距离，不能代替地图接口；当前不引入 Elasticsearch。

## 6. 排班、请假与时间槽

### 6.1 排班模板

- 平台允许工作时间为每天 `08:00—22:00`。
- 服务人员首次使用时设置统一的每日工作区间；每天可以有多个区间，但所有非休息日使用同一套区间。
- 可以一键把工作日设置为 `08:00—22:00`。
- 可以设置每周固定休息日；暂不支持分别配置每个星期几的不同工作区间。
- 首次设置后，只有主动修改排班或请假时才需要操作。
- 缩短排班、修改固定休息日或请假如果与已分配订单的服务槽或缓冲槽重叠，直接拒绝。
- 请假以 30 分钟为粒度，开始时间至少在当前时间 2 小时以后。
- 当前不实现服务人员主动取消订单；紧急无法履约和自动改派以后再扩展。

### 6.2 预约窗口

- 预约开始时间以 30 分钟为粒度。
- 最早预约当前时间 2 小时以后，最远预约未来 7 天，参数配置化。
- 服务时长、排班、请假和缓冲均以 30 分钟为最小粒度。
- 清洁服务距离开始至少 12 小时时，可以选择优惠或标准预约；不足 12 小时只能选择标准预约。
- 维修始终只支持标准预约。
- 优惠接单截止时间为 `min(支付成功时间 + 2小时, 服务开始时间 - 6小时)`。

### 6.3 时间槽模型

每名服务人员预生成 `08:00—22:00` 的半小时时间槽，唯一约束为 `(worker_id, slot_start)`。

时间槽使用以下状态与占用类型：

- `NON_WORKING`：不在工作区间或固定休息日；
- `AVAILABLE`：可以接单；
- `LEAVE`：已请假；
- `SERVICE`：被订单服务时段占用；
- `BUFFER`：被订单缓冲时段占用；
- `SERVICE`、`BUFFER` 另外记录 `STANDARD` 或 `OFFER` 占用类型及分配记录标识。

时间槽滚动保证未来 30 天完整：首次设置排班或新建人员时生成；每天零点只补齐新进入窗口的一天；应用启动时补漏。生成必须幂等，不能覆盖已有 `LEAVE`、`SERVICE` 或 `BUFFER`。

当前缓冲归属于刚完成的订单：

- 标准自动派单结束后占用 120 分钟 `BUFFER/STANDARD`；
- 优惠自主抢单结束后占用 60 分钟 `BUFFER/OFFER`。

取消尚未开始的订单时释放服务槽和缓冲槽，并根据现有排班模板恢复为可用或非工作状态。历史分配由订单分配记录保存，不依赖时间槽保存审计历史。

## 7. 订单、支付与自动调度

### 7.1 订单模型

- 当前一张订单只有一个 SKU、数量固定为 1，最多保存一条成功分配记录。当前不支持改派、取消后恢复原订单或同一订单重新分配；`order_assignment(order_id)` 使用唯一约束，保留分配记录自己的自增ID。
- 订单履约、支付、调度状态分别表达；当前标准派单只有一个任务，其重试信息直接保存在订单表。资金流水、成功分配记录和时间槽占用独立记录，不能用一个巨大状态字段承载所有含义。
- 订单保留分类、项目、SKU、标准价、报价、成交价、时长、服务说明和地址等快照。
- 派单失败、候选不合格或占槽失败记录到 `dispatch_attempt`，不产生成功分配记录。取消或完成时修改已有分配记录的状态，保留人员、分配时间、释放时间与原因、完成时间等信息，不删除记录后重新分配。历史接口的 `assignments` 数组因此为零条或一条，不改变接口结构。
- 分配记录、服务槽与缓冲槽占用、订单状态变更必须在同一事务内提交；一单一条记录的唯一索引不替代抢单状态和价格版本的条件更新。未来确认改派需求后，再通过迁移调整分配模型。
- 客户不能指定服务人员；不同服务分别下单，不做购物车、组合预约或合并支付。

主履约状态大致为：

> 待支付 → 待分配/待抢单 → 待服务 → 已出发 → 已到达 → 服务中 → 待确认 → 已完成 / 已取消

最终枚举名称和各子状态由原型与 OpenAPI 明确。

### 7.2 模拟支付

- 创建订单后进入待支付，15 分钟未支付自动取消。
- 不连接真实支付渠道，但支付、补差、部分退款和全额退款都生成流水并使用幂等业务号。
- 标准订单支付成功后立即自动派单；优惠订单支付成功后进入抢单池。
- 订单是否支付、是否落实人员必须分别表达。
- 已支付订单不能直接修改 SKU、地址或预约时间，需要取消后重新下单；优惠报价调整是唯一例外。

### 7.3 标准自动派单

候选人员必须满足：账号启用、允许派单、具备技能、服务城市符合、所有所需服务槽和缓冲槽可用。

候选排序暂定：

1. 当天已分配服务总分钟数较少者优先；
2. 当天订单数较少者优先；
3. 人员 ID 作为稳定排序。

系统同步尝试有限数量候选人。暂时没有可分配人员时进入 `WAITING_DISPATCH`，每 30 秒扫描一次，也可由排班变化触发重试；最长等待 5 分钟。超时后标记派单失败、取消订单、全额模拟退款并及时通知客户。

当前不存在管理员手工派单或手工改派接口。管理员可以查看候选筛选、尝试结果和失败原因。

### 7.4 优惠抢单

- 只有同时满足技能、城市、排班、请假和时间槽条件的人员才能查看并抢单。
- 抢单前只展示服务判断所需的信息，不展示完整门牌和不必要的联系方式。
- 一人成功后其他人失败；接单后确定成交价格、分配和时间槽占用。
- 截止仍无人接单时关闭入口、取消订单并全额模拟退款，不自动加价或擅自转为标准预约。
- 客户可以在截止前加价或降价；报价、补差、退款、版本更新和抢单相互竞争时必须得到唯一结果。

### 7.5 并发裁决

- 同一优惠订单多人抢单：使用订单状态、`priceVersion` 和条件更新确定唯一成功者。
- 不同订单争抢同一人员：在同一事务内把服务槽与缓冲槽从 `AVAILABLE` 条件更新为占用状态，并校验受影响行数等于预期槽数。
- 任意一组槽更新数量不足，整个事务回滚并尝试下一名候选人，不能留下部分占用。
- 预生成时间槽的唯一索引只保证一名人员一个时间点只有一行；真正的并发占用由条件更新和 InnoDB 行锁完成。
- 时间槽按照 `slot_start` 的稳定顺序更新，减少死锁；当前不再额外对人员执行 `SELECT ... FOR UPDATE`，也不使用 Redis 分布式锁或 Lua 作为最终裁决。
- 重复支付、补差、退款、取消、抢单和状态提交均需幂等。

## 8. 履约、取消与评价

### 8.1 履约

- 服务人员依次执行已出发、已到达、服务中、提交完成等状态操作。
- 客户页面显示服务开始码，人员输入正确开始码后才能开始；它只表示客户参与确认，不作为地理位置证明。
- 人员提交完成后进入待客户确认；客户确认后完成，24 小时未处理则自动完成。
- 当前不强制上传服务照片。

### 8.2 取消

- 待支付：客户直接取消或系统超时取消。
- 已支付但未开始服务：客户可以直接取消、全额模拟退款并释放时间槽。
- 已出发、已到达或服务中：客户不能直接取消，后续售后和异常流程再扩展。
- 服务人员当前不能主动取消已分配订单，也不能通过请假破坏已有订单。
- 管理员可以基于异常取消订单，但必须填写原因；管理员不能手工指定其他人员。
- 改地址、改时间和改服务规格通过取消后重新下单完成；已取消订单不恢复、不重新分配。

### 8.3 评价

- 只有已完成订单可以评价，每单一次。
- 支持 1 至 5 分、准时/专业/服务态度等标签和文字内容。
- 暂不支持修改、删除、人员回复或评价直接改变隐藏信用分。

## 9. WebSocket 与后台审计

WebSocket只负责在线实时通知，写操作仍使用 HTTP。需要覆盖新优惠订单、报价变化、订单被抢、订单关闭、派单成功和派单失败等事件。事件至少携带类型、订单 ID、价格版本和时间。

事务提交后才能发送事件；断线重连或重新登录后必须重新查询当前列表，不能把 WebSocket 当作可靠数据存储。当前单实例可以维护内存连接，未来多实例时再评估 Redis Pub/Sub 或消息队列广播。

管理员维护账号、人员、技能、服务目录、价格、上下架和系统配置，查看订单、支付、调度及异常。修改价格范围、上下架、禁用账号、管理员取消和退款处理等关键操作需要审计日志。

订单、支付、报价变化、调度、分配和操作日志不能物理删除；目录数据可以逻辑删除或下架。

## 10. 工程、技术与接口规范

### 10.1 仓库结构

仓库包含前端、接口契约、数据库基线和可运行的 Java/Maven 基础工程：

```text
home-service/
├── home-service-server/
│   ├── pom.xml                    # packaging=pom，继承与聚合
│   ├── home-service-common/       # 通用响应、分页、基础异常
│   ├── home-service-app/          # 唯一 Spring Boot 应用
│   ├── application-local.example.yml
│   └── database/init/home_service.sql  # 唯一初始化入口，不自动执行
├── home-service-web/      # Vue三端低保真前端
├── docs/
│   └── database/数据库设计文档.md
├── AGENTS.md
└── README.md
```

依赖方向固定为 `home-service-app → home-service-common`；两个子模块继承父 POM，只有 app 执行 Spring Boot repackage。业务模型、枚举、Mapper、认证及 Web/WebSocket 配置全部属于 app，common 不依赖 app 或业务模型。

各子工程拥有自己的 `src`、构建文件和测试目录。仓库根目录不创建含义不明的公共 `src`；SQL随后端工程管理，当前使用 `database/init` 存放空库初始化脚本，已有数据的结构演进以后再新增 `database/migrations`。部署配置在真正开始部署时按实际组件创建。

### 10.2 技术方向

- JDK 17；本机已有 `17.0.12 LTS`。
- Spring Boot 3.5.16、MyBatis-Plus 3.5.17（Boot 3 starter 与分页 jsqlparser）、Hutool core 5.8.47、JJWT 0.13.0；Maven、MySQL 8.0.16+、Lombok。底层 Jackson、MySQL 驱动和 Spring 版本由 Boot BOM 管理，子模块按用途声明依赖。
- `home-service-web` 使用 Vue 3 + Vite + TypeScript，承载客户、服务人员和管理员三套路由与布局。
- `home-service-server` 使用 Spring Boot 模块化单体结构，可由 IDEA 直接打开运行。
- OpenAPI 3.0.3 作为唯一正式 HTTP 接口契约；WebSocket事件在同一契约的描述和 Schema 中说明。
- 开发阶段在 Windows 与 IDEA 运行；最终使用 Nginx 和 Docker Compose 部署。
- 核心阶段使用 Spring 定时任务处理未支付超时、接单截止、派单等待和自动确认。
- WebSocket属于已确认能力；Redis、RabbitMQ、地图和 Elasticsearch均不是核心运行前提。

### 10.3 HTTP接口规范

- API基础路径为 `/api`，三端业务前缀为 `/api/customer`、`/api/worker`、`/api/admin`。
- 三端登录分别放在对应前缀下，客户注册属于客户前缀；共享能力可以复用 Service，但不能绕过角色校验。
- 统一响应结构为 `code`、`message`、`data`；成功码统一为字符串 `SUCCESS`，业务错误码使用稳定的英文字符串，HTTP状态码仍表达真实HTTP语义。
- 分页请求统一使用 `pageNo`、`pageSize`；默认页码为1、默认每页20条、最大100条。
- 分页数据位于统一响应的 `data` 中，字段为 `list`、`total`、`pages`。
- 需要幂等保护的写接口统一使用请求头 `Idempotency-Key`。
- 所有对外 ID，包括 JSON、路径和查询参数中的 ID，均按十进制字符串表达，避免 JavaScript整数精度问题。
- JSON金额使用两位小数字符串，例如 `"128.00"`；后端仍使用 `BigDecimal`。
- 日期时间使用带偏移量的 ISO 8601，例如 `2026-10-02T14:30:00+08:00`；业务时区统一为 `Asia/Shanghai`。
- WebSocket连接路径为 `/ws`，只承载通知；前端收到事件后可以按需通过HTTP重新查询最新数据。
- 前端保持低保真，不制作图片、动画或复杂视觉效果，但导航、表单、筛选、分页、滚动、状态操作和异常反馈必须可用。
- 客户端采用随视口变化的竖屏预约布局，桌面居中、窄屏适应实际宽度，不制作固定尺寸手机窗口。一级导航为首页、订单、我的；二级页面提供返回与稳定操作栏，中间独立滚动。未登录可浏览服务，预约及个人业务要求登录并回到原操作。服务人员与管理员保留独立入口。
- 客户按接口返回的入口、套餐或项目进入简短详情，填写预约信息后进入独立模拟支付确认页。优惠建议价采用最低价与标准价中点向下对齐接口返回的 priceStep 整数倍，再限制在合法报价区间，不是智能预测；客户仍须明确确认报价和预约方式。

### 10.4 执行原则

产品和接口规范已经足以开始实现。后续Codex应直接在合理假设下完成低风险的页面文案、类名和内部实现，并把结果写入OpenAPI或代码；只有发现会改变核心业务规则的矛盾时才暂停询问用户。

### 10.5 前端数据职责与真实联调

- 前端运行时仅调用同源 `/api` 和 `/ws`，没有浏览器 Mock、模式切换、默认测试账号、演示数据、时间推进或故障模拟入口；接口失败正常报错，不能回退成本地成功。
- 浏览器不使用 localStorage、IndexedDB、Web Locks 或 BroadcastChannel 保存业务实体或模拟事务。订单、价格、排班、支付、资格、权限及状态结果均以后端为准；`OrderVO.allowedActions` 是后端按当前操作者裁剪的可执行操作提示，提交时仍须事务和并发复核。
- sessionStorage 仅保留登录会话、账号隔离的未提交表单草稿、幂等键、请求结果待确认标记和合法业务返回来源，不能作为业务数据库。已提交数据重新通过 HTTP 查询；图片在内存中预览并经真实鉴权接口上传/读取，不持久化图片二进制到浏览器数据库。
- 预约时间、报价步长、缓冲、截止规则、地区和上传限制从规则/区域接口读取；目录、服务入口及账号不得以写死的演示数据替代接口响应。普通文案、状态中文映射和正式枚举可以作为代码常量。
- 订单历史包含状态变化及操作者类型、可选原因。客户与人员只能看到经过权限裁剪的历史，不暴露内部账号ID。分配历史以释放时间/原因或完成时间解释 RELEASED/FINISHED；审计使用 targetType + targetId，订单关联查询明确使用 orderId。
- 分类、项目、SKU、技能分别使用 CategoryQuery、ServiceItemQuery、SkuQuery、SkillQuery；公开目录查询不暴露 status，服务端只返回可用目录。
- 前端单元测试限于纯函数边界及静态契约检查，不建立模拟业务数据库。Java 基础工程已建立，27 表结构与真实 MySQL 映射验证结果见 STATUS；不包含种子数据。基础设施验收不代表端到端业务、资源归属、状态机、调度或业务并发验证通过，也不沿用旧35表的执行记录。

## 13. 数据库基线与实施约定

详细字段、索引和业务备注集中维护在 [数据库设计文档](database/数据库设计文档.md)，与 `home-service-server/database/init/home_service.sql` 对齐。

### 13.1 初始化边界与简化原则

- 当前设计为27张InnoDB表，使用MySQL 8.0.16及以上、utf8mb4_0900_ai_ci。脚本只面向空项目库，不包含基础数据、模拟数据、删库或删表语句，也不在应用启动时自动运行。实际初始化状态必须连接后核验，不能从 SQL 文件存在推断。
- 原35表建表文件与开发种子已移除；本地旧表由用户手动处理。新建表文件不是旧库的增量升级脚本，未来已有数据的演进再新增 `database/migrations` 迁移，不反复重跑初始化文件。
- 删除只有身份映射的客户资料表；人员排班区间和每周休息日合并到人员资料；服务和地址快照合并成一对一 `order_detail`；评价标签和允许图片MIME使用结构明确的JSON数组；标准派单重试状态合并到订单。
- 地址簿、技能关系、请假、半小时时间槽以及接口需要的资金/报价/派单/分配/状态/审计历史仍独立保存。没有购物车，也不为未知需求设计万能JSON、预留字段或扩展表。
- 表间采用逻辑外键，不建立物理FOREIGN KEY；Service负责引用存在、角色归属、删除限制和跨表事务，不级联删除业务历史。目录和地址使用逻辑删除，账号使用停用，已有订单始终读取自己的快照。
- 建表结构保留27个主键和14个额外唯一索引，不设置普通查询二级索引，也不添加其他性能索引替代。查询字段、筛选条件、排序和分页规则保持一致；缺少查询索引可能改变性能、扫描范围和锁竞争，不能承诺速度或超时表现不变。基础 Mapper 映射验证不等于业务查询性能测试，后续如需性能优化，应以实际查询和测量为依据另行迁移。

### 13.2 ID、时间、金额和状态

- 普通实体和关系表使用有符号 `BIGINT AUTO_INCREMENT`，Java映射Long；关系表另设业务组合唯一键。行政区和入口使用稳定字符串代码，订单详情直接使用订单ID主键，平台设置固定id=1。对外ID始终按字符串传输。
- CUSTOMER账号ID同时作为customerId；workerId独立，通过人员表唯一account_id映射。JWT和UserContext始终使用accountId。
- 业务日期时间用DATETIME按Asia/Shanghai保存；平台日内时间用TIME，人员JSON排班区间用HH:mm字符串。应用连接和序列化统一业务时区，对外ISO 8601带+08:00，不依赖机器默认时区。
- 金额使用DECIMAL(11,2)/BigDecimal，对外为两位小数字符串。Java只为跨多个类频繁使用的角色、账号、目录、服务类型、预约类型、订单状态和错误码保留枚举，并同时保存英文值与中文说明；其余状态使用与OpenAPI和SQL CHECK一致的字符串，真正编写所属业务时再在就近类中声明 `static final` 常量。订单履约、支付、调度状态仍分字段表达。

### 13.3 关系、历史与并发

- 目录关系为分类→项目→SKU，每单一个SKU且数量固定1，不单独存quantity。服务/地址快照合并成order_detail；订单所需技能保留关系快照，供资格过滤在分页前完成。
- 账号资料、地址簿联系人、订单地址快照和本次订单联系人分别满足不同契约字段。默认地址按第5节先锁客户账号行再维护地址；入口在普通可空字段上唯一，SKU逻辑删除时按第4节释放绑定；成功分配按第7.1节保证每单最多一条记录，不以ACTIVE状态区分是否占用唯一性。不增加契约未要求的目录名称唯一限制。
- 人员排班两个JSON同时为空表示尚未设置；已配置的区间为1—14个，星期集合为0—7个。请假与派单/抢单、排班变更需遵守第7.5节的时间槽锁定顺序，不覆盖有效服务或缓冲。
- `(worker_id, slot_start)`唯一只保证槽行唯一。实际占用需在同一事务内按AVAILABLE条件更新所有服务和缓冲槽并校验影响行数，不足则全部回滚；释放仅匹配本次分配记录。
- 支付business_no全局唯一，评价按order_id唯一，报价历史按(order_id, price_version)唯一。订单保存截止时间、报价/状态版本、优惠发布时间、关闭时间及标准派单重试字段。调度失败尝试与生效分配分开保存。
- 图片保存私有storage_key、摘要、MIME、大小和像素尺寸；绑定后内容不可变。订单图片关系按请求顺序保存sort_no，以(order_id, image_id)唯一约束防止同单重复图片；每单最多三张由第5节的下单校验保证，不额外限制一张图片只能关联一个订单。图片删除与绑定需锁定同一图片行，不能删除已有订单附件。

### 13.4 设置、审计与幂等

- 平台设置为强类型单例，仅earliest_hours/latest_days允许管理端修改；其他字段以OpenAPI固定规则为准，DDL给出默认值，Service校验读取值。图片MIME数组固定JPEG/PNG/WebP。默认值不会自动创建设置行，基础数据留待后续任务。
- audit_log区分USER与SYSTEM，订单相关操作保存明确order_id；资金操作可关联流水、类型和金额。日志只追加并脱敏，不保存密码、JWT或完整敏感请求。
- HTTP幂等作用域为账号+方法+路径+Key；匿名注册使用ANONYMOUS_REGISTER+规范化用户名SHA-256+方法+路径+Key，规范化不改变用户名大小写语义。保存请求指纹和首次成功响应，敏感请求使用带服务端密钥的HMAC-SHA-256指纹，不保存原始敏感内容；失败不缓存，过期记录安全清理后才可重用Key。
- 成功幂等结果与业务写入同事务提交，记录至少保留24小时；不可逆动作仍由业务唯一键、来源状态和条件更新兜底。数据库不使用触发器、存储过程或事件提前实现Service、派单或定时任务。

## 14. 后端基础工程使用与边界

### 14.1 分层和模型

- 基础包 `com.homeservice`，采用 hmall 的 `controller`、`domain/{dto,po,query,vo}`、`service/impl`、`mapper`、`config`、`handler`、`interceptor`、`enums`、`utils`；按账号、目录、订单等职责分子包。Controller 分 customer/worker/admin，依赖 `IXxxService`，实现命名 `XxxServiceImpl`，注入统一 `@RequiredArgsConstructor + private final`。
- 27 个 PO 和 27 个 BaseMapper 覆盖唯一 SQL 基线；明确 Mapper 扫描、MySQL 分页插件与时间填充。自增、字符串主键、订单 ID 主键、设置固定主键分别映射。只保留 `Role`、`AccountStatus`、`CatalogStatus`、`ServiceKind`、`BookingType`、`OrderStatus`、`ErrorCode` 七个共享枚举，英文数据库/JSON值与中文说明分开；其他有限取值不建立全局枚举，`ClientEntryCode` 继续由数据库维护。
- `deleted_at` 只在原有逻辑删除表上使用 NULL/时间语义；生成列 `scope_identity` 可读但禁止 ORM 插入、更新。通用 Mapper 删除 SKU 不等于完成“删除并释放入口”的事务规则。
- JSON 使用明确集合元素和专用 Jackson 类型处理器；两个排班字段的 SQL NULL 表示未配置，空集合含义与 NULL 不同。默认 NOT_NULL 更新策略下，需要清空可空列时由未来 Service 显式 `.set(column, null)`，不能依靠 `updateById` 的 null 值清空。
- DTO、Query、VO 与 PO 分离，响应为 `Result<T>`，分页为 `PageQuery/PageDTO<T>`。`Result` 采用苍穹外卖风格的 Lombok 普通类并实现 `Serializable`，提供两个 `success` 和三个 `error` 重载；字段仍遵守本项目 OpenAPI 的 `code/message/data`，成功码为字符串 `SUCCESS`。包装响应不按每个接口重复创建类；覆盖命名 Schema、嵌套对象和 WebSocket 帧，业务接口仍未实现。
- `domain` 模型统一使用容易阅读的普通 Lombok 类，不使用 `record` 或 Builder 堆叠。每个字段用简短的行尾 `// 中文含义` 说明用途，不在模型字段上写大段 Javadoc；import 只保留实际使用的类型。DTO/Query 只保留请求格式、长度、数值范围和基础交叉字段校验，并为每个约束提供明确中文 `message`；提示文字统一引用 common 的 `MessageConstant`，新增提示先在该类命名后复用，不在注解、异常或错误码中散落文本。VO 不承担输入校验；PO 只保留主键、逻辑删除、自动填充、JSON 类型处理和生成列等确有作用的 MyBatis-Plus 映射注解。
- OpenAPI YAML 继续是唯一正式接口契约和前端代码生成来源，不在模型上重复维护 Swagger `@ApiModel`/`@ApiModelProperty`。代码阅读依靠清晰字段名和行尾中文注释；接口浏览、联调和生成依靠 `docs/api/openapi.yaml`，避免 Java 注解与既有契约出现两份定义。
- Java 源码采用四空格缩进；最后一条 import 后保留空行。非模型类可在职责确有必要时使用简短中文说明；注解各占一行，方法体展开书写。
- ID 仅对 ID 字段转为十进制字符串，范围为正的有符号 BIGINT；金额用 BigDecimal/两位小数字符串；时间严格 `+08:00`、精确到秒。统计及分页数值保持数值。可选未发生字段省略，必需 nullable 字段保留 null；`SkuDTO.clientEntryCode` 缺失非法、显式 null 合法。
- JSON 拒绝未知字段、重复键、非法共享枚举、违反局部状态约束的字符串、数字金额、浮点整数和无偏移时间；路径、查询也使用严格转换，公开目录 Query 不接受 status/sortBy/isAsc。普通字符串裁剪后校验，密码保留原文；密码同时满足契约字符长度与 BCrypt 的 UTF-8 72 字节上限，超限拒绝、不截断。

### 14.2 认证、异常与通知

- 错误处理固定分为三层：DTO/Query 用 Bean Validation 拦截与数据库和业务状态无关的格式错误；Service 校验资源归属、账号/订单状态、金额资格、幂等、事务与并发条件，失败时抛出带稳定 `ErrorCode` 的 `ApiException`/`BusinessException`；`GlobalExceptionHandler` 是 HTTP 失败响应的统一出口。
- Controller 在正常路径只返回 `Result.success(...)`，不在 Service 或 Controller 中到处 `return Result.error(...)`。`Result.error(...)` 的重载保留给全局异常处理器和框架错误入口组装统一响应。用户能够修正的字段校验原因放在 `data.fieldErrors`，顶层 `code/message` 保持契约稳定；正常的空列表、未找到可选结果或布尔判断按方法语义返回，不滥用异常。
- 全局异常输出 `code/message/data` 并保留真实 HTTP 状态，业务码来自 OpenAPI。`expectedPrice`、`priceVersion` 等并发保护字段校验失败时只返回通用的报价已失效提示，不向前端解释内部版本机制；请求解析和未知异常同样不回显字段实现、SQL、堆栈或凭证。生产仅有框架错误处理入口，没有登录、注册、me、订单等业务 Controller，也没有开发登录后门。
- HS256 JWT 配置化签名密钥和有效期，载荷使用 accountId/role/exp；请求校验 Bearer 格式、算法、签名、过期和载荷，并经最小只读 `IAccountQueryService` 查询真实账号的存在、状态和角色。UserContext 只保存账号身份，完成、异常及异步移交后清理；workerId 必须另查人员资料，不能当成 accountId。
- 公开白名单精确到 HTTP 方法和路径且只能取 OpenAPI 公开集合。三端路径角色检查不代替资源归属、状态迁移或优惠资格校验，这些由未来 Service 实现。
- `/ws` 握手拒绝 URL 查询参数；5 秒内首帧 AUTH，认证前无业务数据，成功返回 AUTHENTICATED。按契约使用 4401/4403，管理认证超时、Token 到期及断线清理。身份保存在独立会话绑定中，不读取 HTTP ThreadLocal。
- Origin 默认同源；跨源开发在配置中逐项填写明确的 http(s) Origin，不使用 `*` 或全局 CORS 放行。`NotificationSender.afterCommit` 只能在业务事务中登记明确 accountId/role 接收者，提交后发送，回滚不发；没有全局广播或抢单资格过滤，未来必须先做业务接收者筛选。
- 仅准备私有上传目录配置，没有上传存储、内容检查或附件业务鉴权接口。未增加审计 AOP、业务定时任务、Redis、MQ、真实支付或地图 SDK。

### 14.3 IDEA 与 Maven 启动

1. IDEA 打开 `home-service-server/pom.xml` 并导入父工程及两个模块；Project SDK、Maven Importer/Runner 均选 JDK 17，启用 Lombok 注解处理。运行主类 `com.homeservice.HomeServiceApplication`，模块 classpath 选 app，工作目录为 `home-service-server`，profile 为 dev。
2. 将 `application-local.example.yml` 复制成同目录的 `application-local.yml`，填本机数据库密码和至少 32 随机字节的 Base64 JWT 密钥；该文件已 Git 忽略，不能加入版本控制。也可直接提供 `DB_PASSWORD`、`JWT_SECRET_BASE64` 环境变量。开发默认数据库 `127.0.0.1:3306/home_service`、用户 root、HTTP 8080；可用 `DB_HOST/DB_PORT/DB_NAME/DB_USERNAME/SERVER_PORT` 覆盖。
3. dev 从**运行工作目录**导入本机文件；test 用 `TEST_DB_*` 配置；prod 使用环境变量模板和默认 `VERIFY_IDENTITY`，不是部署结果。`JWT_TOKEN_TTL` 默认 2h，`UPLOAD_DIRECTORY` 配置私有目录，`WS_ALLOWED_ORIGINS` 配置逗号分隔的明确源。必需数据库/JWT 配置校验失败即拒绝启动。
4. 数据库必须由用户手动初始化；应用、测试不执行初始化或迁移 SQL。启动时连接真实 MySQL 并只读探测账号表，失败直接启动失败；这一步不代替下述全表一致性验收。连接会话显式设置 `+08:00`，不依赖 MySQL 命名时区表。

在 `home-service-server` 工作目录执行（确保 `java -version`、`mvn -version` 都使用 JDK 17）：

```powershell
mvn clean verify
# 另需通过环境变量提供真实库的 DB_PASSWORD 等配置；密钥由测试进程随机生成。
mvn clean verify -Pmysql-it
java -jar home-service-app/target/home-service-app-1.0.0-SNAPSHOT.jar --spring.profiles.active=dev
```

普通 `clean verify` 运行静态映射、契约模型、MVC 和实际网络 WebSocket 协议测试；受控账号查询替身仅存在于测试源集的 protocol 配置，不能注入生产。`mysql-it` 额外启动真实应用、先比对全部表/列/主键/唯一索引/CHECK，再只读调用所有 Mapper，并在同线程事务内创建少量映射夹具，强制回滚并复核未留下记录；不依赖预置业务账号、不修改已有记录。事务回滚不会复原 MySQL 自增序列，可能留下正常 ID 间隙。

配置文件的本机导入相对于工作目录；Maven 测试工作目录是 app 模块，因此数据库集成测试推荐使用环境变量。真实库未初始化或不匹配时不得运行映射夹具，测试会在结构检查处失败。测试没有 H2，不重建表、不导入种子。

依赖选择参考 [Spring Boot 3.5 要求](https://docs.spring.io/spring-boot/3.5/system-requirements.html)、[MyBatis-Plus 安装](https://baomidou.com/getting-started/install/)、[分页插件](https://baomidou.com/plugins/pagination/) 和 [JJWT](https://github.com/jwtk/jjwt)，固定解析后的补丁版本；未覆盖 Boot 管理的底层版本。BCrypt 规则参考 [Spring Security 密码存储](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)。工程组织主要参考本机 hmall，苍穹补充多端/配置/DTO/VO，黑马点评补充 MyBatis-Plus 使用习惯，未复制课程全套依赖。

## 人员端交互与聚合口径

- 人员端使用随视口高度变化的竖屏布局，首页、订单、我的三个一级入口；首页展示优先任务和抢单池，标准分配无需接受/拒绝。任务优先正在服务、已到达、已出发，再按预约时间展示待服务，待确认最后。
- 抢单池全量资格过滤后排序再分页，固定按优惠支付成功正式入池的发布时间升序、同时间按数值意义字符串ID升序（无浮点精度丢失）；调价不改变发布时间，不提供排序切换。新单自动进入全局后部，失效单自动移除；保留阅读位置并去重补位，不绕过尚未加载旧单；通知期间确认价格保持不变，冲突展示原价与最新价重新确认。WebSocket仅限页面在线通知，以HTTP权威结果自动同步，约30秒可见页面补漏，恢复可见、网络恢复与重连重新同步；合并并发，不用旧响应覆盖新结果，仅异常显示重试连接。
- 人员订单全量排序后分页：进行中（服务中、已到达、已出发）、待服务、待确认、历史；同组预约时间升序，历史按实际关闭时间closedAt降序、ID稳定排序。
- 人员仅可自助修改联系电话；姓名、账号、技能、城市、账号状态和调度资格由平台维护。统计由独立完整聚合接口返回：Asia/Shanghai今日预约且待服务数量，以实际完成确认时间closedAt计本月及累计完成订单；时长仅为已完成订单预约时长，无收入或结算含义。
- 月历展示未来30天与所选月份交集，合并相邻同类工作、服务、缓冲、请假区间；缓冲不算空闲，工作时间内空闲不保证任意服务可接。沿用统一工作区间与每周休息日，不增加逐日排班；请假冲突返回本人对应订单。
- 应用内返回遵守业务层级，切换一级导航和接口返回的服务分组不堆积历史；订单详情返回原任务或列表并恢复筛选、滚动。支付结果顶部返回本次服务所属套餐或维修项目列表，底部另有返回首页和查看订单；合法业务来源按账号及订单保存，刷新恢复，无法确定时首页兜底。待支付退出返回订单详情。普通错误统一在内容顶部浮层提示2秒，字段错误及报价冲突、支付不确定状态持续展示至处理。

- 两端“我的”直接展示称呼与身份，资料同一弹窗内查看与编辑，人员仅编辑电话、客户编辑称呼和电话。人员统计以文字摘要直接展示，月历直接展示；工作时间、请假、记录、规则和退出确认使用紧凑入口与弹窗。客户地址簿和预约复用一个地址面板，新增后选中并保留预约草稿。旧深链接兼容至对应面板，不重复维护页面。
- 弹窗锁定背景并恢复位置，正文滚动且操作栏可到达；真正未保存修改关闭时确认放弃，故障保留输入。两端订单分组为共用单行可横向滚动标签，不改变业务状态和排序。创建成功、模拟支付成功、人员安排成功分别说明，普通成功与错误统一顶部反馈，支付不确定/冲突/退款/安排结果在正文持续展示。
